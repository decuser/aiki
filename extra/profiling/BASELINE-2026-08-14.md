# Profiling baseline — 2026-08-14

This is the first baseline produced by Aiki's correlated semantic/substrate
profiler after the profiling implementation itself was audited for attribution
overhead and concurrent execution. The semantic counts are properties of these
Aiki executions. Host timing, sampled CPU proportions, and allocation figures
must be re-established on the normal Aiki development machine before they are
used to judge an optimization.

The development sweep recorded its environment in `manifest.txt`. This run used
Go 1.23.2 in the implementation container while the repository declares Go
1.24.0, and the binary was compiled against disposable compile-only stubs for
uncached Ebiten/readline dependencies. None of the six workloads exercises
those facilities, but these timings remain developmental rather than canonical.

| concurrency | 15000 | 5001 | 50001 | 5000 | 5000/5000 | 0/0 | 202 ms | 32.7 MB |

`interval alloc` is the `runtime.MemStats.TotalAlloc` delta taken immediately
around evaluation of the user AST. Prelude loading, entry-file lexing/parsing,
and module-registry setup are outside that interval. Module imports performed
by the user program are inside it.

## CPU correlation snapshot

CPU profiles are statistical samples, not exact counters. The following layer
shares are from this single run and should be treated as evidence of where to
look, not as fixed properties of the workloads.

| workload | semantic CPU samples | substrate CPU samples | principal labeled substrate region |
|---|---:|---:|---|
| evaluator loop | 100% | 0% | — |
| tail recursion | 100% | 0% | — |
| list append | 15.6% | 84.4% | `_append`, `<prelude>:71` |
| store + bits | 95.3% | 4.7% | split among bits/store primitives |
| regex/ffi | 72.9% | 27.1% | `_regex_match` |
| concurrency | 60.0% | 40.0% | chiefly `_apply` in this sample |

Shorter CPU profiles can move materially between runs. In an earlier regex run,
for example, the semantic/substrate split was substantially different. The
stable evidence is that both regions are visible and correlated; optimization
claims should use repeated runs rather than one percentage.

## Findings

- Source attribution originally dominated several workloads because source text
  was split into lines on every semantic hit. Caching source lines in `Env`
  removed that measurement distortion before this baseline was recorded.
- Concurrency race testing exposed a deeper execution-state bug: function calls
  were taking their dynamic call stack from the lexical function environment.
  `NewCallEnv` now keeps lexical name lookup and dynamic stack/probe state
  separate, so isolated spawned computations do not reconnect through prelude
  calls. The concurrent profiling paths are race-clean in the audited packages.
- List append is the clearest substrate-side cost. The CPU profile is dominated
  by `_append`, and the ordinary Go allocation profile attributes about 96% of
  sampled allocation space to `halAppend`. The 1.88 GB interval allocation for
  15,000 persistent appends makes this a strong implementation signal.
- Store + bits has a very different shape. It performs 640,005 semantic calls,
  and CPU sampling is overwhelmingly in semantic/evaluator regions. Its Go
  allocation profile also shows substantial evaluator/call-environment work.
  That points toward dispatch/environment cost before store representation.
- Regex/ffi visibly crosses both layers. `_regex_match` is identifiable as the
  substrate region, but the exact semantic/substrate CPU share is sample-noisy
  and should be established with repeated runs before optimization.
- The evaluator-loop and proper-tail-recursion drivers remain useful substrate-
  independent baselines: their sampled CPU is entirely in semantic regions.
- The synchronized concurrency driver confirms that exact semantic call/send/
  receive counts and CPU labels survive spawned execution when completion is
  expressed through ordinary channel protocol.

## Allocation-profile caveat

The Go `allocs` profile is an ordinary process-level sampled allocation profile.
It does not carry Aiki pprof labels, and it also contains allocations from
startup work such as parsing and registry setup. Therefore:

- measured-interval `alloc_bytes`, `mallocs`, and `gc_cycles` answer **how much**
  allocator/GC activity occurred while evaluating the Aiki program;
- the Go alloc profile answers **which Go allocation sites were hot in the
  process**;
- the alloc profile must not be presented as exact Aiki-source-correlated
  allocation attribution.

## Interpretation rule

Aiki semantic counts answer **what computation occurred**. CPU labels answer
**where Go spent sampled CPU while realizing that Aiki context**. Measured-
interval memory statistics answer **how much allocation/GC activity occurred**.
The ordinary Go allocation profile answers **which Go allocation sites were
hot**.

Do not collapse these into a single synthetic cost number, and do not optimize
from a single sampled run. The purpose of this baseline is to make subsequent
measurement comparable and inspectable.
